# 莫提斯插件开发

```
读规范 → （新来源）调研并报告结论 → 用户确认 → 搭目录 → 先写测试 → 实现 → 热加载验证 → 交付
```

插件开发也是开发任务，计划、提交和验收都照 `mortis-dev` 做。本技能只补充插件特有的部分。

## 1. 先读

- `docs/` 下的《插件规范》：目录、id、停用规则、import 检查、三种插件的约定。和本技能冲突时以规范为准。
- `src/mortis/plugin_api.py`：接口和每个方法的注释，开头写着 `candidates` 返回值的格式。
- 参照现成的实现：数据类型带来源看 `plugins/galgame/`，播放看 `plugins/system_player/`。
- 字段目录的定义在 `src/mortis/catalog/spec.py`，内置类型的字段在 `src/mortis/catalog/` 下。

## 2. 选种类

- 给一个新类型做字段目录：写 `data_type` 插件，这个类型专用的来源放进它的 `sources/` 里一起发布。
- 给已有类型（电影、电视剧、动漫，或别的插件的类型）补来源：写 `source` 插件。
- 打开本地文件的另一种方式：写 `player` 插件。网页内播放还没做，不要写。

先定 id：小写字母、数字和下划线，以字母开头。id 一旦有人用过就不能改，因为快照、设置、密钥和登录都按它存。名称以后随时可以改。

## 3. 接新来源前先调研

动手写来源之前，先回答下面这些问题，用一份短报告交给用户决定接不接。每条结论都要能复现：数字写明样本量和怎么抽的样，范围边界要有反例，没测到的写明原因。

- **收录范围**：收了哪些作品，没收哪些。按类别各抽几条搜一下，看有没有结果，不能只看网站自述或首页。
- **活跃度**：最新条目的时间，最近几个月新增多少，是否还在更新。
- **访问方式**：有没有公开 API；要不要账号、令牌或 OAuth；限速和失败的样子；有没有拦截页、验证码、地区限制。写明是从哪个网络环境测的。站点条款是否允许。
- **字段**：每个字段在样本里的出现率和质量；外部编号怎么得到；常见的脏数据（占位符、别名、多值分隔）。
- **增量**：和已有来源比，哪些字段是它独有的、哪些是重复的。只有重复字段的来源不值得接。
- **语言**：标题、简介、人名分别是什么语言。
- **接入方案**：服务哪个数据类型；填哪些字段、不填哪些；在默认来源顺序里排第几、为什么。准确性无法核对的字段只能排在有官方数据的来源后面。
- **风险**：改版就会失效的解析点、单人维护、没有 API 契约，以及这次没验证到的地方。

报告先写结论：接或不接；接的话写清类型、字段和排序。调研过程和用过的工具不写进报告。

调研时不要把私人密钥、令牌写进仓库或报告里。公共凭据只用官方文档里公开的那份。

## 4. 搭目录

```
plugins/<id>/
  plugin.toml
  __init__.py          定义 PLUGIN
  sources/             只有数据类型插件带来源时才有
    __init__.py
    <来源 id>.py
```

- 先在仓库的 `plugins/` 里开发；程序自带的插件也放这里。
- `plugin.toml` 写 `id`、`name`、`version`、`kind`；数据类型插件把带的来源列在 `[[sources]]` 里，名单要和 `PLUGIN.sources` 完全一致。
- 包内模块之间用相对导入。只 import 标准库、`pydantic`、`mortis.plugin_api`。
- 联网只用 `host.get_json` / `post_json` / `get_text`；开播放器只用 `host.launch` / `open_default`。

## 5. 先写测试

照 `test-driven-development`：先写会失败的测试，再实现。

- **来源**：参照 `tests/test_plugin_vndb.py`，用假 Host 按地址返回录好的响应，并记下插件发出的请求。至少覆盖：
  - 搜索结果的标题、原名、别名、年份；
  - 详情里没有这一条时抛 `SourceError`；
  - `candidates` 对每个字段给出的值，格式要符合值类型；
  - 设置或密钥不全时 `enabled` 和 `disabled_reason` 的返回值；
  - 令牌被拒时抛 `SourceAuthError`（需要登录的来源）。
- **录下来的响应**放在 `tests/fixtures/<来源 id>/`，只留用得到的部分，去掉令牌、账号和个人信息。测试不连真站。
- **数据类型**：参照 `tests/test_plugins.py`。至少覆盖：注册表能加载它，字段目录能通过校验，默认来源顺序写进了库，停用后它带的来源一起停。
- **播放**：用假的 `PlayerHost` 记下 `launch` 或 `open_default` 收到的参数，断言程序和参数列表正确。

## 6. 实现时注意

- `fetch` 返回完整的原始结果，宿主整份存成快照。`candidates` 只从快照里取值、不联网，这样再次刮削时不用重新请求。
- 出错就抛 `SourceError`，消息写给用户看，不带令牌和完整地址。不要 `except Exception` 之后返回空结果。
- `requests_per_second` 按来源的限速规则声明，不要在插件里自己 sleep。
- 字段键只用所服务类型的字段目录里有的键。

## 7. 热加载验证

写完单元测试后，在真实的宿主里加载一次：

- 开发服务托管仓库里的 `plugins/`。启动和停止照 `mortis-serve` 做。
- 打开 设置 → 插件管理，点「重新加载插件」，确认插件出现、没有错误。数据类型插件要确认它带的来源列在它下面。
- 来源插件到 设置 → 来源 → 该来源：设置表单正常，填了密钥以后提示消失。
- 在测试库里刮一条，在详情页看各字段的值和来源对不对。只用测试库，不要刮用户的真实库。
- 停用、再启用一次，确认开关的联动和《插件规范》写的一致。
- 想单独给用户试一个插件，也可以把文件夹放进数据目录的 `plugins/`。同 id 时它会整包覆盖程序自带的那个。

## 8. 完成标准

- 非 e2e 测试、`ruff format` 和 `ruff check` 都通过；改了前端的话 `npm run check` 和 `npm run build` 也要通过。
- 用到的录制响应里没有令牌和个人信息。
- 在设置页走过一遍第 7 步，向用户报告：插件做了什么、填哪些字段、默认排第几、还有哪些已知限制。
- 默认来源顺序或者字段目录变了，同步更新《技术方向》里的来源列表。
